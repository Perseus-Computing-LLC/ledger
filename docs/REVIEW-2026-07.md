# Plutus deep-dive review — 2026-07

Scope: full-repo review at `main` (v1.0.1). Every claim below was verified
against source and the live test suite (`pytest tests/ test_plutus.py` →
**284 passed** on the reviewed tree, Windows / py3.14). Findings that are fixes
already landed are marked ✅; open items carry a severity and land in the punch
list at the end.

## Verdict

Plutus 1.0.1 is a **genuinely solid billing core**. The money path is
integer-micro-dollar exact, the ledger is append-only with in-SQL
`balance_after`, Stripe reversals converge idempotently, and the self-serve
surface is hardened (CSRF fail-closed, DB-backed signup cap, security headers,
CSV-injection defense, fail-closed public bind). The pre-1.0 security carryover
(v0.7.1 items #28/#30/#32/#33/#37) is **closed in code**, not just in the issue
tracker. Shipped state matches claimed state: v1.0.1 is tagged, on PyPI, and on
GHCR.

The gaps are now second-order: a couple of correctness edges around the
*embedded* SDK, a stale roadmap doc, three unguarded version literals, and one
missing test that the roadmap itself asked for (real concurrency). None block
what's shipped; all are worth closing before the external security review and
the Perseus/Perseus-Vault convergence.

The highest-leverage next move is not in this list — it's the **Hermes per-model
spend attribution** fix (its own PR), which corrects the single biggest source
of wrong numbers Plutus consumes. See §5.

## 1. Architecture

Two layers, deliberately decoupled (`plutus_agent/__init__.py:11-14`):

- **Root FinOps tools** (standalone, stdlib-only, no install):
  - `plutus.py` — provider credit & spend **monitor**. Fuses live balance APIs
    (DeepSeek, OpenAI) with the local Hermes `state.db` cost ledger; emits a CLI
    table, `--json`, or an HTML dashboard. Own `VERSION` (independent line).
  - `plutus_route.py` — runway **router**. Reads `plutus.py --json`
    (`plutus_route.py:173-194`) and rewrites Hermes `config.yaml` so the
    highest-runway provider runs its flagship. Own `VERSION`.
- **`plutus_agent/` package** — the monetization *engine* (PyPI `plutus-agent`):
  - `client.py` — the embeddable **Meter** SDK (local SQLite or remote
    `/v1/usage`).
  - `metering.py` — `record_usage()`, the single revenue funnel: resolve
    workspace → price → insert immutable `usage_events` → debit ledger →
    threshold alerts (`metering.py:81-213`).
  - `db.py` — multi-tenant SQLite schema (orgs → workspaces → users),
    append-only `credit_ledger`, `usage_events`, idempotency tables, integer
    money helpers, `immediate()` `BEGIN IMMEDIATE` context.
  - `server/` — stdlib `ThreadingHTTPServer`: `app.py` (routing, ingest,
    webhook, CSRF, admin), `api.py` (JSON + CSV/JSON export), `views.py` (HTML),
    `auth.py` (Google OIDC + CSRF token + signup gating).
  - `billing/stripe_client.py` — Checkout / Portal / webhook handling.
  - `bridge.py` — hardened subprocess bridge to `plutus.py --json` for the live
    runway panel (absolute-path + allow-list, fail-closed).
  - `pricing.py`, `alerts.py`, `config.py`, `reports.py`, `demo.py`, `utils.py`,
    `integrations/` (framework adapters + Claude Code hook).

**Data flow (usage → debit → read-back):** `record_usage` prices the event,
inserts an immutable `usage_events` row, then debits via `add_ledger(org, -cost,
…)`. The ledger is append-only; each row's `balance_after_micros` is computed
in-SQL. Balance reads back as `SUM(delta_micros)` over the ledger; spend windows
as `SUM(cost_micros)` over `usage_events`.

## 2. Money-correctness

- ✅ **Integer micro-dollars (#38).** All money is `*_micros INTEGER`
  (`db.py` schema); conversion only at the boundary (`usd_to_micros` /
  `micros_to_usd`). No float money columns remain; legacy REAL→micros migration
  present.
- ✅ **Prepaid hard-stop (#28) — default-on and enforced inside the debit
  transaction** on the hosted path. `DEFAULT_CONFIG["pricing"]["block_over_balance"]
  = True` (`config.py`); the ingest path runs `record_usage(..., commit=False)`
  inside `with db.immediate(conn)` (`app.py`), and the balance check is decided
  in integer micros. See finding **P1** for the SDK caveat.
- ✅ **Atomic `balance_after` + free-tier quota race (#30).**
  `balance_after_micros` is computed in the INSERT itself; the quota read and the
  insert are serialized under `BEGIN IMMEDIATE` on `/v1/usage`.
- ✅ **Stripe reversals (#60).** `charge.refunded` / `dispute.created` /
  `funds_withdrawn` reverse the ledger, `invoice.payment_failed` duns; reversals
  converge to a per-ref cumulative target so partial/repeat/replayed events never
  double-reverse; disputes with no customer are mapped back via the PaymentIntent
  on the original top-up; the whole apply is one serialized transaction.
- ✅ **Negative-value guards (#61 cost, #80 tokens)** — double-layered
  (authoritative check in `metering.py`, boundary check in `app.py`);
  `strict_int` also rejects float token counts.

## 3. Security posture (v0.7.1 carryover — all closed)

- ✅ **#32 CSRF** — `_same_origin()` falls back to the request `Host` when
  `base_url` is unset and returns `False` when neither an expected host nor an
  Origin/Referer is present (fail-closed); plus a per-session HMAC-SHA256
  synchronizer token validated with `compare_digest`.
- ✅ **#33 signup abuse** — DB-backed per-day org-creation cap
  (`count_orgs_created_since`, default `max_new_orgs_per_day = 50`) layered with
  the in-memory hourly limiter and per-IP throttle.
- ✅ **#37** — 500s return a random ref id (no `str(e)` leak); the 404 body
  escapes `path`; the OIDC unsigned-token bypass is gated behind
  `auth.allow_unsigned_tokens` (default `False`).
- ✅ **#36 OIDC JWKS** — RS256 id_token signatures are verified against Google
  JWKS before claims are read, with `aud`/`iss`/`exp`/`nonce`/`email_verified`
  checks. Note: the RS256 / EMSA-PKCS1-v1_5 verification is hand-rolled — a prime
  candidate for the planned external review (finding **P5**).
- ✅ **Deploy hardening (1.0.1)** — `_guard_insecure_bind` fails closed
  (`SystemExit`) on a non-loopback bind with auth disabled unless
  `allow_insecure` is set; the demo image sets it explicitly.

## 5. Future state / highest-leverage next moves

1. **Hermes per-model spend attribution** *(shipped as a separate PR alongside
   this review).* Plutus reads the Hermes `sessions` row, which attributes every
   token to the model active when the session *started* — so a mid-session
   `/model` switch corrupts per-provider spend, and with it the runway
   projections and the router's decisions (a provider with hidden burn looks
   like it has infinite runway and gets *more* traffic). Consuming the schema-v17
   `session_model_usage` table (authored + fixed upstream in hermes-agent, issue
   #51607) fixes attribution at the source. Highest leverage because it corrects
   the accuracy of the numbers everything downstream is computed from.
2. **Close the punch list below** before the external security review and the
   Perseus / Perseus-Vault convergence.
3. **Distribution (Phase 3)** — the engine is an SDK + an HTTP `/v1` surface;
   the fastest reach is an MCP server exposing spend/balance/topup as tools, plus
   marketplace listings. Tracked in `docs/partner-targets-2026-07.csv`.
